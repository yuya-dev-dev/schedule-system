# 正式運用ランブック

[資料案内](README.md) | [開発ロードマップ](development-roadmap.md)

## 対象と前提

この手順は、Render Free Web ServiceとNeon Free PostgreSQLを使い、実在案件を扱う10人弱の正式運用を対象とする。共通パスワード、Neon接続情報、バックアップ設定ファイル、バックアップ本体、実在案件情報はGit、README、会話、スクリーンショットへ保存しない。

Neon Freeのinstant restoreは短時間の事故対応に使えるが、長期保持の代替にはしない。2026年7月19日時点の公式情報では、Freeプランの復元履歴は最大6時間、手動スナップショットは1件である。重要な変更前はNeon Consoleで手動スナップショットを作成し、日次の論理バックアップを別に保持する。

バックアップ保管先は、会社が承認し、アクセス制限と暗号化が有効な領域だけを使用する。リポジトリ、GitHub、Renderのローカルファイルシステム、個人用の未承認クラウドストレージは使用しない。

## 日次自動バックアップ

管理用Windows PCのタスクスケジューラから、PowerShell 7で日次バックアップを実行する。ログイン時、ネットワーク接続から30秒後、補助として3時間間隔の確認をきっかけに、取得可能な機会に1日1回取得する。テザリングでも利用できる。

その日の取得が成功し、dumpとSHA-256の整合性が確認できれば再取得しない。設定変更やファイルの破損・削除を検出した場合は取り直す。同時起動はタスク設定とファイルロックで防ぎ、通信やDockerの障害で失敗した場合は、次の実行機会に再試行する。

タスクは設定を作成したWindowsユーザーのログイン中に、管理者権限を使わず実行する。PCの電源OFF・ログアウト中は取得しない。接続時間が短い場合や回線障害時も取得できないことがあるため、実行したかどうかではなく最終成功日時を確認する。

タスクはWindows Script Hostの非表示ランチャーを経由し、PowerShellの起動時にもコンソールを表示しない。同日取得済みならDockerを起動せず終了する。未取得でDockerが停止している場合は自動起動し、エンジンの準備完了を待ってから取得する。正常稼働中のDockerは再起動しない。

バックアップ処理が自分で起動したDockerは、取得成功を記録した後に他の稼働コンテナがないことを確認してから終了する。元から起動していた場合、取得失敗時、コンテナの稼働状況を確認できない場合は終了しない。Dockerの終了失敗は取得結果とは分け、ローカル記録の `DockerCleanupStatus` に残す。終了処理中に中断した場合は `Pending` が残るが、取得成功の記録は維持する。Docker起動時のダッシュボード表示はアプリ側の設定に従う。

### 保存と接続の保護

保存先はOneDrive・Gitの外にある `%LOCALAPPDATA%\ScheduleSystem\Backups` とする。Docker版PostgreSQLクライアントでcustom formatのdumpを作成し、SHA-256ファイルを併記する。過去14日より古い `schedule-system-*.dump` と対応するSHA-256ファイルは、バックアップが成功した後に削除する。

認証設定は同じくリポジトリ外に置き、パスワードをWindowsのDPAPIで保護する。同じWindowsユーザー・同じPCだけが復号できる。保管先のアクセス制限とディスク暗号化を有効にし、バックアップ本体をGitへ追加しない。

Neonにはプーラーを使わず直接接続する。`sslmode=verify-full` と固定クライアントイメージ内のシステムCAで、接続先の証明書とホスト名を検証する。検証に失敗してもTLSモードを弱めない。バックアップ用URLに認証情報を含めず、TLS関連オプションは `sslmode` だけを指定する。Renderの接続設定とは分けて管理する。

PostgreSQLクライアントは、検証済みの公式イメージのdigestへ固定する。Dockerが停止していれば起動を試みるが、テザリング中の不要なダウンロードを避けるため、自動実行では未取得のイメージをpullしない。初回とPostgreSQLメジャーバージョン変更時には、クライアントの互換性とイメージの取得を確認する。

この構成の保存先は本番DBと管理用PCであり、3-2-1-1-0ルールを満たすものではない。別媒体・別拠点・オフラインまたは改変不可のコピーは、保管先の承認を含めた別の運用設計が必要になる。

### 初期設定と運用確認

`Initialize-PostgreSqlBackup.ps1` で認証設定を作成し、初回取得と隔離復元の成功を確認してから、`Register-PostgreSqlBackupTask.ps1` で定期タスクを有効にする。設定したユーザーとタスクの実行ユーザーを一致させ、別ユーザーの同名タスクは上書きしない。

Windows Script HostでJScriptを実行できることを前提とする。登録前にランチャーの起動確認を行い、ポリシーなどで実行できない場合は既存タスクを変更しない。

タスクスケジューラの状態とPC内の成功記録を確認する。終了コード0でも、オフラインや同日取得済みとして処理を終えた場合があるため、取得成功の証拠にはしない。認証情報や設定を変更した場合は、取得・隔離復元と自動実行を再確認する。

失敗時はローカル成功記録の `Status` と `FailureCode` を確認する。Docker未準備、クライアントイメージ未取得、取得処理失敗、archive検証失敗を区別し、例外本文や接続情報は記録しない。

取得日時、対象バックアップ名、検証結果、ログはPC内のアクセス制限された領域で管理し、リポジトリには記載しない。業務終了後などに追加取得が必要な場合は、`Backup-PostgreSql.ps1` を使用する。

## 復元確認

月1回、またはバックアップ方式・Migration変更の後に、最新バックアップを隔離コンテナへ復元する。本番Neon、Render、既存DBへ書き込む操作は行わない。

`Test-PostgreSqlBackup.ps1` はSHA-256とarchiveの読取りを検証し、ネットワークのない使い捨てPostgreSQLへ復元する。必須テーブル、Flywayの失敗履歴がないこと、主要制約、各テーブルの件数を確認し、終了後に検証用コンテナを削除する。実施日、担当者、対象バックアップ名、成功結果はリポジトリ外の運用記録へ残す。バックアップ内の実在データは会話やGitへ出さない。

## 復旧目標

- RPO（目標復旧時点）は、日次バックアップの成功を前提に最大1営業日を目標とする。自動実行はPCの接続機会に左右されるため保証値ではなく、最後に成功した取得時点を確認する。Neonのinstant restoreでより新しい時点へ戻せる場合があっても、長期保持の保証としては扱わない。
- RTO（目標復旧時間）は現時点で未計測とし、保証値を設定しない。月1回の隔離復元では開始から検証完了までの所要時間を運用記録へ残し、復旧手順全体の実測結果が得られた時点で目標値を決定する。

## 誤削除またはデータ破損

1. 利用者へ編集停止を連絡し、発生時刻と対象を記録する。
2. 6時間以内の事故ではNeon Consoleのinstant restoreを使い、まず別ブランチまたはプレビューで復元時点の内容を確認する。
3. 直近の手動スナップショットがある場合も、先にプレビューで内容を確認する。
4. 長時間前の事故、またはNeon復元で解決しない場合は、最新の論理バックアップをこのランブックの隔離手順で検証する。
5. 本番への切替・復元は、ユーザーと導入判断者が対象時点と影響範囲を確認してから行う。復元前の状態を失わないよう、先に現時点のbackupまたはsnapshotを取得する。
6. 復元後は、作業日から1か月を過ぎたデータが残っていないこと、一覧・詳細・保存が動くことを確認する。

## RenderまたはNeonの障害

1. Render Dashboardで直近デプロイとログを確認し、秘密値や実在案件情報を共有しない。
2. Render障害時は、サービス復帰とNeon接続可否を確認する。無料枠のスリープ復帰は障害と区別する。
3. Neon障害時は、Neon StatusとConsoleでプロジェクト・branchの状態を確認する。
4. 接続情報、Migration、バックアップを推測で変更しない。必要なら直近バックアップの隔離復元でデータの可用性を確認する。

## 共通パスワードの変更

共通パスワードの管理と変更作業は管理担当者だけが行う。秘密値自体は会話や文書に書かない。

共通パスワードを15分以内に5回誤ると、その送信元からのログインは15分間拒否される。認証後は30分の無操作でセッションが失効し、月間画面のログアウト操作でも直ちに失効できる。試行制限はアプリのメモリ上で管理するため、再起動時にリセットされる。

1. 新しいパスワードを安全な経路で決める。
2. Renderの `SCHEDULE_ACCESS_PASSWORD` を更新し、再デプロイ後に新旧パスワードでアクセス結果を確認する。
3. 利用者へ新しい値を安全な経路で共有する。
4. 変更日時と担当者だけを運用記録へ残す。

## Accepted Risk / Future Improvement

10人弱の現行運用では、利用者ごとのアカウントを持たない共通パスワード方式を意図的に採用する。この方式では利用者単位の認可、個別失効、操作主体の識別ができず、パスワード漏えい時には全案件へ同じ権限でアクセスされるリスクが残る。

長く推測困難なランダムパスワードを使用し、共有先を必要な利用者に限定する。漏えいまたは利用者変更の疑いがある場合は、管理担当者がRenderの値を直ちに変更し、全利用者へ安全な経路で再共有する。現行運用では個人別ログインや権限管理を導入せず、利用規模や運用要件が変わった場合に再検討する。

## Manual Verification Required

次の項目はGitリポジトリだけでは確定できない。値そのものを文書や会話へ転記せず、Render、Neon、バックアップ保管先の管理画面または設定で確認する。

- Renderで有効なprofileが`cloud`であること
- RenderのDB接続情報と共通パスワードが秘密値として設定され、ログへ出力されていないこと
- Renderが外部から受け取った`X-Forwarded-For`を信頼境界で上書きし、Springの送信元アドレス判定を偽装できないこと
- Neonのアプリ実行ロールとFlyway実行ロールが、運用に必要な範囲を超える権限を持たないこと
- 本番JDBC URLで`channelBinding`を使用する場合、意図した値とPgJDBCの対応状況が一致していること
- バックアップ保管先のACLと保存時暗号化が有効であること

## 正式運用の継続確認

- 会社承認済みの保管先、自動実行するPCとWindowsユーザー、管理担当者、運用記録の場所が決まっている。
- 本番Neonから初回バックアップを取得し、隔離復元が成功している。
- 実施日、担当者、対象バックアップ名を記録している。
- 日次バックアップと月1回の隔離復元結果を、実在案件情報や秘密値を含めず社内の運用記録へ残す。
